# 个人分支提交与同步

默认流程为检查分支、暂存工作区、提交、同步最新主干、推送个人分支。用户明确要求执行这套流程时，这些步骤均在本次授权范围内。仅展示、审核或讨论 Skill 时执行只读操作。用户明确限定文件或步骤时，以该次要求为准。

## 确认仓库和分支

- 读取仓库约定，定位仓库根目录，核对当前分支、upstream、远端、工作树和暂存区。目标主干依次取自用户明确要求、已有 PR 或仓库约定、远端默认分支。优先用 upstream 确定推送远端与目标分支；没有 upstream 时使用唯一可确认的远端和当前同名分支。多个候选无法确定时说明具体候选，请用户选择。
- 当前分支为 `main`、`master` 或已确定的目标主干时，报告分支并暂停写操作。detached HEAD 或存在未结束的 merge、rebase、cherry-pick、revert 时，同样先报告状态。用户明确授权对应的分支处理后再继续。
- 检查推送目标也属于个人分支。upstream 若指向 `main`、`master` 或目标主干，应先明确正确目标。记录已确定的个人分支、远端和主干，后续操作均在该个人分支执行。

## 暂存工作区

- 默认从仓库根目录执行 `git add -A`，包含本仓库全部未忽略的新增、修改和删除。用户指定文件或变更块时只暂存对应范围；已有暂存内容超出该范围时先说明并确认归属，保留其原有状态。
- 核对 `git diff --cached --stat`、`git diff --cached --name-status` 和完整暂存差异，运行 `git diff --cached --check` 及仓库要求的相关检查。检查失败时报告原因和已暂存范围，按用户授权处理后再继续。
- 暂存区为空时跳过业务提交。完整流程继续核对同步与推送；用户只要求本地提交时报告没有可提交的改动。

## 提交当前改动

- 使用 `<type>(<scope>): <主题>`，scope 不明确时省略。按实际影响选择 `feat`、`fix`、`refactor`、`style`、`docs`、`test`、`chore`、`perf`、`build`、`ci` 或 `revert`。默认用中文写主题和可选正文，用户明确要求英文时均改用英文。主题写清本次实际变化，必要时用正文补充重要细节。
- 报告拟使用的提交信息后执行一次普通 `git commit`，保留 hooks。用独立参数或消息文件传给 Git，预先去掉 `Co-authored-by:` 尾注。提交失败时报告具体原因、工作区和暂存区状态，停止后续同步与推送，保留现有修改。
- 成功后核对实际提交信息、提交编号及文件范围。实际信息若仍含 `Co-authored-by:` 尾注，或 hooks 带入范围外的内容，报告差异并暂停后续步骤，不自行 amend、跳过 hooks 或重写历史。必要的主干合并提交属于后续同步步骤。

## 同步最新主干

- 业务提交后重新检查工作区和暂存区。存在剩余已跟踪改动或暂存内容时暂停同步并报告；新出现的未跟踪文件需确认不会被合并覆盖。同步前保持当前修改可恢复，不自动 stash、丢弃或把检查产物混入提交。
- fetch 已确定的主干及远端个人分支，记录最新主干完整 SHA。fetch 失败时停止同步并报告已经完成的提交。远端个人分支存在且不是本地 `HEAD` 的祖先时，报告领先或分叉的提交，等待确定同步方式。
- 使用已 fetch 的远端主干检查祖先关系。主干已经是 `HEAD` 的祖先时直接核对差异；当前分支可快进时使用 `git merge --ff-only`。两边分叉时使用 `git merge --no-ff --no-commit`，先检查合并后的差异和相关验证，再创建一条独立同步提交。同步提交沿用提交语言、hooks 和尾注规则。
- 遇到冲突时核对双方的业务变更，在已明确的需求内处理。无法确定取舍时说明具体文件与冲突，保留当前状态并暂停。验证失败时报告合并状态和原因，待处理后继续。
- 合并完成后确认最新主干是 `HEAD` 的祖先，再检查 `git diff <远端主干>...HEAD` 是否符合本次功能范围、是否带入旧功能。Squash 合并后仍按实际祖先关系同步。树内容未变化时，可复用同一份代码的验证结果。

## 推送个人分支

- 完整流程在同步及检查通过后执行推送。用户只要求暂存或本地提交时，完成对应步骤即可。
- 推送前重新核对当前分支、远端与目标个人分支，检查远端最新指针。存在远端分支时 fetch 并确认它已包含在本地历史中；发现并行更新时报告差异。使用普通 push，由 Git 处理检查后再次出现的远端竞争。
- 显式推送 `HEAD:refs/heads/<个人分支>` 到已确定远端。首次推送使用 `--set-upstream`。推送失败时报告原因和已完成步骤；成功后用远端分支指针核对是否等于本地 `HEAD`，不一致时报告并行更新。
- 流程终点是个人分支推送成功，由用户继续提交 PR。改写历史、强推、创建或合并 PR、打 tag、部署均需要各自的明确授权。

## 交付

按实际完成的步骤报告个人分支、暂存文件范围、提交信息与编号、验证结果和工作区状态。执行过主干同步时补充主干 SHA 与合并结果，执行过推送时补充远端、目标分支及核对结果。中途停止时说明已完成步骤、当前 Git 状态和剩余工作。
