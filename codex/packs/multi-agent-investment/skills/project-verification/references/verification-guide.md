# 验证选择与结果交付

所有仓库路径相对仓库根目录。先核对当前文件，下面是现有入口，不是要求每次完整执行的脚本；不要直接整段运行。

## 1. 按改动选择

| 改动 | 基础检查 | 扩大范围的条件 |
| --- | --- | --- |
| 文档／Skill | 引用、格式、空白；Skill 使用可用的创建器校验工具 | 只检查文档，不启动应用。校验器缺失时报告限制，不自动安装。 |
| 前端 | 对应 `web/tests/*.test.mjs`、`web` 内 `npm run verify` | 共享请求、组件或状态逻辑改动，扩展相关前端测试；可见布局与交互补浏览器验收。 |
| 后端 | 对应 pytest，确认测试用例与风险相关 | 共享服务、存储、权限、接口兼容或影响难以局限时，运行完整后端测试。 |
| 前后端联动 | 接口相关测试及调用方测试，再检查构建 | 在隔离 API/Web 验证请求、响应、加载与错误；仅单元桩通过不能证明真实接口互通。 |
| 数据库相关 | 阅读存储初始化／迁移实现，确认是否真的改结构 | 有迁移时检查旧结构升级、重复初始化和旧数据兼容；只改查询不假定需要迁移，不拿开发库试验。 |

没有已有测试可覆盖时，明确缺口；补写测试或新增故障预览需要纳入实际开发范围，不能用无关测试通过代替。

## 2. 前端命令

在仓库根目录选择适用命令，先检查 Node 与依赖是否已具备：

```sh
node --test web/tests/api-pagination.test.mjs
node --test web/tests/*.test.mjs
(cd web && npm run verify)
git diff --check
```

第一行是分页相关的定向示例，其他功能选实际存在的测试文件；第二行是扩大前端回归时使用的命令。`web/package.json` 当前没有 `npm test`，不要臆造；`verify` 包含字体检查与生产构建，不包含 Node 测试或浏览器验收。

依赖缺失时不自动 `npm install`、`npm ci` 或改锁文件。`git diff --check` 不覆盖未跟踪的新文件，需另外检查本次新增文件的空白和引用，不为检查而暂存文件。

## 3. 后端命令与顺序

先按 [环境指南](local-environments.md) 确认隔离、资源归属及数据库没有被其他验收使用。容器化测试使用仓库已有组合，以下测试命令要求相应镜像已按当前代码构建：

```sh
docker compose -f compose.test.yaml -f compose.perf.yaml up -d --wait db-test
docker compose -f compose.test.yaml -f compose.perf.yaml --profile tests run --rm test-runner python -m pytest -q tests/test_decision_run_pagination.py
docker compose -f compose.test.yaml -f compose.perf.yaml --profile tests run --rm test-runner
```

定向与完整测试按范围选择，不要求重复执行。`Dockerfile.test` 默认执行 pytest；旧镜像可能包含旧源码，必须核对。镜像缺失或过时需构建时先说明影响并取得所需授权，不隐式下载依赖或假装已验证新代码。

已具备 Python 及项目开发依赖的机器也可按 `README.md` 使用宿主机 pytest，显式设置 `TEST_DATABASE_URL` 指向已核对的本机 `db-test` 映射；不要使用日常 `.env` 的数据库。无需为运行测试复制作者的本地文件。

`tests/conftest.py` 在每次测试前 `TRUNCATE` 业务表。正确顺序是：确认独立库可用 → 功能测试 → 结束测试进程 → 适用的测试数据准备 → 性能或浏览器验收。不要并行执行后两类工作与 pytest；预览中也不要启动清表测试。

pytest 默认有网络测试桩，`live` 测试需显式开关才启用。普通验证不启用该开关；测试桩通过不代表真实供应商可用，也不自动适用于单独启动的 API。

## 4. 专项与浏览器验收

- 分页性能：参考 `docs/decision-runs-pagination.md` 和 `scripts/benchmark_decision_runs.py`。仅在本次明确需要时使用；脚本会写入并替换其负责的测试记录，先核对目标与归属。记录数据规模、条数、字节数和耗时，不承诺与线上相同速度。
- 邮件正文：参考 `docs/email-preview.md` 的纯预览流程及 `scripts/preview_notification_emails.py`。脚本输出可本地重新生成，但其中实发有固定个人收件人限制，不将它当作通用发送工具，不自动配置 SMTP 或执行发送选项。
- 页面预览：先核对浏览器实际 URL、API 目标和代码版本，再检查相关加载、错误、空状态、权限及正常数据。角色和状态使用已有隔离测试账号／桩；缺失时报告未验收，不使用真实账户制造写操作。
- UI 检查按任务覆盖中英文、长内容、窄屏、键盘和缩放。只在现有环境支持时使用可选 Mock；不因缺少 Mock 跳过可执行的公共测试。

## 5. 结果交付

使用简短清单，逐项记录检查对象、环境、实际命令和结果，状态用“通过／失败／阻塞／未执行”。说明跳过原因和实际未覆盖的风险。

区分：测试通过 ≠ 构建通过 ≠ 健康检查通过 ≠ 浏览器流程通过。历史文档中的通过次数、截图和性能数据不能算作本次证据。浏览器预览不代表已覆盖全部角色、真实行情、邮件客户端或生产环境。

不要贴完整环境变量、带凭证的连接串、私有日志或真实用户数据。报告资源是复用还是本次创建，以及最终保留或停止了哪些资源；不自动生成报告文件、提交或推送。
